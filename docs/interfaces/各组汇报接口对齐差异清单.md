## 0 目的与范围

IW-IF-STD-001 的 V1.0 与 V1.1 两稿是**架构与接口规范单元在未与其他组沟通的前提下独立拟定的内部草案**，
其中的话题名、坐标系名、串口字段与频率均属推定值。

本文件记录：拿该草案逐条比对**五组已完成的方案汇报**后，发现的全部**冲突、缺口与需实测事项**，
以及逐条的裁决结论。它是 IW-IF-STD-001 V1.0（正式第一版）全部改动的依据。

裁决口径（经项目组确认）：

- **能定的定**——纯接口命名、语义、频率、QoS 类问题由本单元直接裁定并给出依据；
- **需实测的标 TBD**——依赖硬件选型、实测数据或采购结论的，标记责任组与解除条件，本版不替其做工程决策；
- **不替其他组做电气/机械设计决策**——本文件只约束**接口**，不约束实现。

### D2 SLAM 框架

| 项 | 内容 |
|---|---|
| 分歧 | SLAM s3/s6/s7/s14 通篇按 Google **Cartographer** 展开（含 `.lua` 配置、`optimize_every_n_nodes` 等）；环境 s9「**slam_toolbox**……作为 Cartographer 的现代替代方案」、环境 s16「建图**直接采用 slam_toolbox**」 |
| **裁决** | **基线为 slam_toolbox，Cartographer 列为备选。二者不得同时运行**（同一时刻只能有一个节点发布 `map→odom`）。选用哪一个由自动导航与 SLAM 算法组在仿真联调前定标并登记 ICR。 |

| 落点 | §5.2 TF 所有权注；§4.1 环境基线表注 |

### D3 坐标系命名（本次最重要的一项）

| 项 | 内容 |
|---|---|
| 分歧 | SLAM s9「核心拓扑结构：map → odom → **base_link** → **laser_link**」、SLAM s13「TF 坐标树结构 map → odom → base_link → laser_link」、SLAM s6「tracking_frame = "**base_link**"」、SLAM s7「tracking_frame = "base_link"，published_frame = "odom"」、SLAM s10「header.frame_id = 'base_link'，child_frame_id = '**laser_link**'」；标准 §5.1/表 6 为 `map → odom → **base_footprint** → base_link` 与 `**laser_frame**` |
| **裁决** | **保留 `base_footprint` 与 `laser_frame`。** 即：<br>① 主链为 `map → odom → base_footprint → base_link`，**`base_footprint` 层不得删除或改名**；本车无悬架，`base_footprint → base_link` 允许为仅含安装高度的固定变换。<br>② 雷达坐标系名为 **`laser_frame`**（不是 `laser_link`）。<br>③ SLAM 侧的 `tracking_frame` 应填 `base_footprint`；若实现上必须用 `base_link`，则须满足上一条零变换前提并在配置注释中说明。<br>④ `published_frame` 保持 `odom`，与标准 §5.2 一致（SLAM 发布 `map→odom`）。 |
| 依据 | REP 105 移动平台坐标系约定；`laser_link` 与 `laser_frame` 混用会直接导致 TF 断树与 `/scan` 数据无法转换，属 P1 级问题（标准 §9.2）；`base_footprint` 是已发布口径，改名成本高于保留 |
| 落点 | §5.1 增补命名兼容条款；§5.2；表 6-1；`interface_registry.yaml` 的 `tf_frames` 加 `constraint` |

### D5 上位机与下位机的链路拓扑

| 项 | 内容 |
|---|---|
| 分歧 | 标准 §6 标题为「上位机与下位机串口协议」，术语表把下位机定义为「ESP32 **或** STM32」，隐含**单段**链路；底盘 s3「STM32 管实时控制，**ESP32 管通信接入**」、s4「上位机 / 调试（串口·WiFi）→ ESP32-WROOM-32 通信网关 → STM32F407VET6 运动主控」、s8「里程计与状态回传……**经 ESP32 上报上位机**」、s10「ESP32 侧：手柄接收、上位机串口、协议打包下发（50Hz）」 |
| **裁决** | 明确为**两级链路**：<br>① **上位机 ↔ ESP32 网关**：走标准第 6 章串口帧（SOF `AA 55` + CRC-16/MODBUS），**这是唯一的跨组串口接口**。<br>② **ESP32 ↔ STM32**：底盘组内部链路（UART 二进制帧，CRC8 校验，20 ms 心跳），**不上浮为公开接口**，标准不约束其帧格式。<br>③ 但 ESP32 **必须**把 STM32 的遥测（`BASE_STATE`、`A1`、`A2`、`A3`、`A4`）透传为第 6 章规定的 `MCU → HOST` 帧，并以 `serial_bridge` 为唯一 ROS 2 侧端点。<br>④ 手柄若由 ESP32 直接解析，`/wheelchair/cmd_vel/teleop` 的发布方记为「ESP32 网关节点」，与 `serial_bridge` 为同一进程亦可。 |
| 依据 | 底盘组为底层控制本职，其双 MCU 分工已是决策稿；板间帧属其内部实现，纳入标准只会增加无谓耦合；但**遥测透传必须约束**，否则上位机拿不到里程计与安全状态（IF-07 验收依赖于此） |
| 落点 | §6.1 增链路拓扑声明；术语表「下位机」改为「对上位机呈现为单一串口端点的网关设备（ESP32）」；新增图 1 架构框图 |

### D6 心跳与超时

| 项 | 内容 |
|---|---|
| 分歧 | 标准 §6.6「MCU 连续 **300 ms** 未收到有效 HOST_HEARTBEAT 或 CMD_VEL 时，立即把底盘速度置零」；底盘 s8「优先级：急停 > 心跳看门狗 > 手动限速 > 正常规划。急停或心跳丢失时，目标速度在 **200 ms** 内强制降到 0」、s3「安全机制：硬件急停 + 看门狗，**200 ms 内强制停车**」 |

### D7 超声波上报频率

| 项 | 内容 |
|---|---|
| 分歧 | 标准表 5「/wheelchair/ultrasonic/ranges …… 10 Hz」、表 8「0xA4 ULTRASONIC_STATE …… 10 Hz」；电气 s11「HC-SR04……数据刷新率达 **50 Hz**」 |
| **裁决** | **主题与消息频率均改为 50 Hz**，10 Hz 记为**下限**（允许在算力受限时降频，但不得低于 10 Hz）。 |
| 依据 | 电气组为传感器所有者且给出明确能力值；50 Hz 对避障安全阈值（30 cm）响应更优。带宽核算：50 Hz × 4 路 × 约 21 B ≈ 42 kbit/s，115200 bit/s 链路余量充足 |
| 落点 | 表 5-1 及串口表 6-4；`registry` 的 topics 与 message_ids |

### D8 速度上限的层次

| 项 | 内容 |
|---|---|
| 分歧 | 标准 §4.5-4「实物初期线速度上限为 **0.20 m/s**、角速度上限为 **0.40 rad/s**」；底盘 s9「最大线速度 **2.0 m/s**（调试限 **0.5**）」「最大角速度 **3.0 rad/s**」 |
| **裁决** | **不是冲突，是三个不同层次的量，标准须显式区分**：<br>① **安全上限**（上位机安全过滤器与固件共同强制）：实物初期 0.20 m/s / 0.40 rad/s，存于 `config/real/safety_limits.yaml`；<br>② **台架调试限速**：0.5 m/s / 0.3 m/s²，底盘组 `config.h` 内部量，仅在架空轮或单轮台架使用；<br>③ **机械设计上限**：2.0 m/s / 3.0 rad/s，属机械与电机能力边界，**不得作为运行配置**。<br>三者关系：① < ② < ③。 |
| 依据 | 底盘组数值为设计/调试参数，标准数值为安全门禁；混为一谈会让读者误以为标准过低或底盘组超标 |
| 落点 | §4.5 新增第 6 条说明三层关系 |

### D9 云端大模型与离线语音

| 项 | 内容 |
|---|---|
| 分歧 | 标准 §2「云端大模型仅通过 HTTPS 提供非安全关键的意图解析服务」；语音 s6「离线识别，本地 AI 推理，断网也能用」「隐私安全，语音数据不上传云端」、s5「离线语音交互入口」、s7「原生 ROS 2 话题 + CAN + 串口」 |
